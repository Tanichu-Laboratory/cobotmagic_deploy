# 把持位置ずれのログ分析（2026-09-17）

対象は最新の `action_commands_20260917_093711.csv`（349 publish / 11要求 / 73.52秒）。
直前の093451実行（360 publish / 12要求）も比較した。
今回キューブに接近・把持を試みているのは左腕。設定・制御コードは変更していない。

## 結論

最新ログでは、左腕のIKがモデル位置目標を崩す問題は主因と考えにくい。
モデルの把持位置と実物キューブとの位置合わせが不十分で、長い開ループ実行により
閉じる直前の視覚修正が入らないことが主因候補。
ただしキューブの3D座標や学習時のカメラ・把持点定義との比較情報がないため、
視覚認識、カメラ取り付け差、グリッパー形状・把持点差のいずれかまでは断定できない。

## 確認できたこと

- 校正ログは `mode=tool`、`joint_signs=[1,1,1,-1,1,-1]`。前回のフレーム修正が反映されている。
- 全349行で左の `raw_left == target_left`。モデル位置を橋渡し中にクリップ・変形していない。
- 左のIK位置残差中央値は0.001 mm未満。最大4.332 mmは初期接近中。
  関節変化量制限は15/349で発動するが、接近後・把持区間の左IK残差はほぼ数値誤差。
- request3以降の9観測で、実測関節からのFKと実測EEFの位置差は中央値1.125 mm、最大1.893 mm。
- request11直前の実測EEFと直前送信目標の位置差は1.783 mm。
  実測関節FKと実測EEFの差は1.432 mm、姿勢差0.869°。
  観測は直前publishの0.182秒後。全時刻での収束を保証する値ではない。

## 画像と更新間隔

request4、request5、request11の左手首画像では、緑のキューブが指の間より画像右側へ寄って見える。
特にrequest11のモデル入力画像にはすでに位置ずれが見えるが、生成された冒頭動作は
大きな横位置修正をせず、ほぼ同じ位置で閉じる。
単眼投影の見え方なので、画像だけから正確な3Dずれ量や左右方向の実機補正値は算出しない。

カメラのコード上の割り当て（front→head、left→left_wrist、right→right_wrist）、
RGB変換、OpenWAM標準前処理の使用は確認した。
これだけでは学習時と実機のカメラ位置・画角・指先形状・把持点が一致することの検証にはならない。

## 切り分けの優先順位

1. `open_loop_steps` を4〜8にした比較で、接近後・閉動作中にも新画像で再計画させる。
   5 Hzと約0.4秒の推論なら要求間隔は概算1.2〜2.0秒となる。
   視覚位置合わせ自体の誤りを必ず解消する方法ではなく、更新遅延の寄与を調べる実験。
2. 同じ対象・位置で手首画像とモデル目標を比較し、ずれの方向が一貫するか確認。
   学習時のカメラ位置/画角、ロボットのnative EEFと実際の把持中心、指先形状の差を照合する。
3. 把持中の実測EEF・画像をpublishごとにも保存すれば、閉じた瞬間の追従誤差を直接評価できる。
   現状画像とEEFは要求時点のみで、連続動画やキューブの真の3D位置はない。

右腕には別途、実測関節FKと実測EEFの差が最大9.697 mm（request11）残る。
左の空振り把持の主因とは分けて扱う必要があり、双腕全体の運動学が完全一致したとは結論しない。
