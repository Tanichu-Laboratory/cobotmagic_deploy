# OpenWAM実機の小さい動作：ログ診断

対象: `logs/action_commands/action_commands_20260917_080359.csv`、同時刻のrequest_snapshots。
タスク `put cubes into the box`。69件のpublish記録、9要求、31.205秒。
解析とIK再計算はオフラインで実施。実機への指令、制約設定、ブリッジコードは変更していない。

## 確認できた原因

### 1. 姿勢角の±π境界で制限方向が逆転する

EEFにも通常のベクトル差分 `target-current` を使い、そのまま±0.03radにクリップしている。
角度の周期性を処理していない。
右腕step9のroll: 基準 -3.128479 → モデル +3.138555rad。
単純差は+6.267034rad、短い角度差は-0.016151radだが、実際には+0.03radを適用した。
左腕step21も短い角度差+0.033826radに対して-0.03radを適用。
いずれかのEuler成分の単純差がπを超える記録は右44/69、左5/69。
これは実装上の明確な不具合であり、姿勢追従の悪化とIK目標のずれを引き起こす。
修正はSO(3)上の姿勢差制限を優先。Euler各成分のwrapだけでは特異点・表現分岐の問題は残る。

### 2. EEFで `reference: current` が実測姿勢を参照していない

`ros_bridge_node.py` のpublish処理は、EEFモードで `publish_current_*` に
`command_*`（前回目標）を代入している。結果として実測EEF基準の制限になっていない。
CSVの `publish_current_*` も実測EEFではないため、実測評価には要求時の `current_*` とsnapshotを用いた。
要求開始時の指令基準と実測位置の乖離は最大 左28.3mm、右51.1mm。
IKで実現できなかった分を指令側が先へ進めるため、追従誤差が蓄積する。

### 3. 小さい位置目標に対してIK残差が大きい

位置クリップは各軸6mm。位置クリップ発生は左12/69、右22/69。
姿勢クリップは左22/69、右58/69。
IK位置残差の中央値: 左6.776mm、右10.781mm。最大: 左26.183mm、右39.671mm。
設定の許容残差は40mmなので、6mm程度の移動を実現できなくても採用され得る。
ログに残らないpublish拒否の回数は、このCSVのみでは確定できない。

先頭ログを実際の観測関節値・EEF姿勢・URDF・設定でオフライン再計算:

| 腕 | 目標xyz変位(mm) | IK解のFK変位(mm) | 位置残差(mm) |
|---|---|---|---:|
| 左 | [-0.990, +0.697, +3.776] | [-1.359, +0.768, +0.887] | 2.913 |
| 右 | [-6.000, -3.870, -3.788] | [-1.488, -3.066, +2.563] | 7.831 |

この例では関節deltaのクリップは発生していない。
IKの正則化を0にした比較でも残差と関節deltaクリップが残ったため、
正則化だけを主因として解除することは適切ではない。
解の採用条件には既報の `converged OR 最終残差条件` 問題もあり、最終解で判定すべき。

### 4. 実効指令周期が設定5Hzより遅い

同一チャンク内のpublish間隔中央値は0.412秒、約2.43Hz。
全69記録は約31.2秒。要求間隔は約3.5～3.8秒、モデル応答は中央値0.399秒。
先頭観測を使ったIK再計算は片腕約0.14秒、両腕約0.28秒（オフライン参考値）。
IKとブリッジの処理時間が周期を押し下げていることと整合し、モデル通信待ちだけでは説明できない。

## モデル出力と実際の動き

前回指令基準に対するモデル位置差の中央値は左3.20mm、右3.38mm。
モデルの先頭8ステップには元々小さい目標も多く、全てが6mm制限で縮小されたわけではない。
実測位置（9要求時点）の可動範囲xyzは左[46.7,17.2,30.4]mm、右[34.4,65.9,55.0]mm。
通信は機能しており、実測上も数cmの範囲で動いている。
モデルがタスクを進めない理由や、捨てている後半24ステップの効果は、保存された先頭8ステップだけからは確定できない。

## 修正の優先順位

1. EEF姿勢をSO(3)の差で制限し、最新の実測EEFとその鮮度を参照する。
2. IKの最終出力の残差判定を厳密化し、不採用時に前回指令状態を進めない。
3. IK解法・重み・URDF/実機フレームの整合をログ再生で評価し、小さい位置移動を実現できるか確認。
4. 上記を直した後に制御周期と位置制限を評価。制限値の単純拡大は先に行わない。

## IK前後・publish後の誤差分解（084939実行）

実行中ROSログに記録された校正用関節角と、CSVの初期EEF姿勢から補正行列を再構築。
全62指令で、送信関節角のFKとモデル目標の距離を再計算した。
CSVに記録されたIK位置残差との最大差は0.0005mm未満で、実際に使われたIK計算の再現を確認。

- publish前のIK解位置誤差: 左中央値19.348mm・最大37.707mm、右中央値19.075mm・最大32.184mm。
- したがって、送信してロボットが動く前の目標関節角の時点ですでに誤差が存在する。

初回チャンク最終指令（index31）と、次要求時点の実測を同じ座標系で比較:

| 誤差段階 | 左(mm) | 右(mm) |
|---|---:|---:|
| モデルEEF目標 → IK送信角度のFK | 37.707 | 10.959 |
| IK送信角度のFK → 実測角度のFK | 5.947 | 1.790 |
| 実測角度のFK → 実測EEF | 47.561 | 18.332 |
| モデルEEF目標 → 実測EEF（全体） | 74.297 | 18.490 |

上記は誤差ベクトルの長さなので単純加算はできない。ベクトル自体の和は全体誤差と一致することを検証済み。
観測はindex31送信の約2.44ms後であり、最終目標への収束評価ではない。
実測関節はむしろ一つ前のindex30の送信値に近く、6関節の最大差は左0.145°、右0.141°。
これは直前の関節指令には概ね追従していることを示すが、全時間帯の駆動系精度を保証するものではない。

左Zの段階別例（ベース座標、m）:
モデル目標0.307816 → IK送信角のFK0.271910 → 実測角のFK0.271061 → 実測EEF0.247435。
IK解の段階で約35.91mm低く、関節追従に相当するFK差は約0.85mm、FKと実測EEF間でさらに約23.63mm低い。

結論: publish後の駆動だけが原因ではない。既にIK解に大きな残差があり、さらにFK/実機EEF対応にも不整合がある。
URDF・末端フレーム・関節対応・観測時刻の照合とIK収束条件の改善を優先する。
詳細数値: `logs/openwam_ik_diagnosis/stage_breakdown_084939.json`。


## IK修正とオフライン再検証（084939の62ステップ）

変更:

1. IKをROSから独立した `common/piper_ik.py` に移し、実機I/Oなしで再現可能にした。
2. OpenWAMでは関節角正則化を0とし、URDF範囲内のtrust-region least squaresに変更。
   旧正則化は誤差を残してでもseed付近に解を留める目的関数であり、位置追従と競合していた。
3. 解を関節変化量上限で制限した際は、その範囲内でさらに位置・姿勢残差を最小化。
   符号・単位・EEF目標を変更したり、関節上限を緩和したりする処理は加えていない。
4. 制限前の収束フラグで制限後の残差判定を通過する不具合を修正。
   判定・記録の対象は、実際に送るfloat32関節角のFK。
5. publishに失敗した目標でcommand履歴が先行更新される不具合を修正。
6. 各publishの実測seed、制限前解と残差、制限発動、制限後FKをCSVへ追加。

比較結果（位置、mm）:

| 段階 | 左 中央値 / 最大 | 右 中央値 / 最大 |
|---|---:|---:|
| 保存ログの旧送信角度 | 19.348 / 37.707 | 19.075 / 32.184 |
| 旧送信角をseedに新IKで再求解、変化量制限なし | <0.001 / 3.865 | <0.001 / <0.001 |
| 新IKの連続再生、変化量制限前 | <0.001 / 3.865 | <0.001 / <0.001 |
| 新IKの連続再生、変化量制限後の送信候補 | <0.001 / 20.840 | <0.001 / 7.392 |

連続再生は「前の新指令へ実測関節が完全追従した」と仮定して次seedを更新する。
旧ログには各publish時点の実測seedがないため、実機軌道の厳密再現・改善率の保証ではない。
元ログのIK残差再現差は最大0.0005 mm未満。
左の制限前最大3.865 mmはrequest1/index9でJ5上限1.22 radに当たる解。
他の枝を含む大域的な到達不能の証明ではない。

変化量制限は左11/62・右3/62で発動。制限後5 mm超の候補は:

- 左request2/index0: 20.840 mm、index1: 8.637 mm、index2: 5.279 mm。
- 右request1/index0: 7.392 mm。

現設定ではこれらも既存の最終許容残差40 mm内として受け入れられる。
すべてのpublish前残差を5 mm以下にした修正ではない。
制限前解は新設の5 mm・0.05 rad閾値以下が必要で、制限後には既存40 mm・0.8 radを別途確認する。
変化量制限を維持して各目標への厳密到達も要求する場合、同一目標の分割実行など実行時間の扱いが別途必要。

ROS Python 3.8で計算時間中央値は片腕約6.1 ms（この保存入力でのオフライン参考値）。
回帰・変換・通信テスト計36件成功。実機publishや稼働中プロセス再起動はしていない。
URDF FKと実機end_poseの不整合は今回の数値IK変更では修正していないため、実機EEFの改善は未確認。

## 092132実行: 基部ヨー回転の原因とフレーム修正

最新CSVは8 publish、初回〜最終1.302秒。0番関節の初期角からの変化:

| 腕 | 最終送信角の変化 | 最終publish前の実測角の変化 |
|---|---:|---:|
| 左 | -42.406° | -32.093° |
| 右 | +32.426° | +27.422° |

したがって過大な基部回転は送信指令に存在する。最終指令への実測収束値ではない。
同じ8ステップのモデル位置目標差分（各腕ベースxyz）は、左[-7.576,-0.525,+23.359] mm、
右[-9.572,-4.788,-7.578] mm。少なくともこの実行区間では+X方向への前進目標ではない。
左の目標姿勢変化は約2.262°、右約4.154°であり、基部へ数十度のヨーを直接命令しているわけではない。

### 確認できた運動学の不整合

旧実装は `T_measured(q0) @ inv(FK(q0))` を左側のベース補正として適用していた。
左のベースZ軸を実測座標で[-0.417,+0.873,+0.252]へ傾け、
モデルの左位置差分[-7.576,-0.525,+23.359] mmをURDFでは[-13.721,-18.475,+8.586] mmへ変換していた。
末端フレームの差までベース回転として扱うため、目標移動方向そのものが変わっていた。

加えて、このローカルURDFのjoint4・joint6は軸が `0 0 -1` で、
ROSの関節角との対応には符号反転が必要だった。
6軸の符号64通りを21組の実測関節/EEFで照合すると、左右とも `[1,1,1,-1,1,-1]` が最良。
符号を合わせたFKに対し `inv(FK(q0)) @ T_measured(q0)` を右側の末端補正にすると、
異なる関節姿勢での実測EEFとの整合が大きく改善した。
これはこのURDFとROSトピックの組合せについての検証結果であり、全Piper構成への一般化ではない。

最新の初期観測1組で校正し、それ以外の20組で検証した誤差:

| 対応方法 | 左 位置中央値/最大(mm) | 右 位置中央値/最大(mm) | 左/右 姿勢中央値(°) |
|---|---:|---:|---:|
| 旧ベース補正・符号そのまま | 6.107 / 66.716 | 14.235 / 63.573 | 2.902 / 11.060 |
| 末端補正のみ・符号そのまま | 2.492 / 39.173 | 12.446 / 39.071 | 2.492 / 9.403 |
| 末端補正＋符号対応 | 0.149 / 3.755 | 1.053 / 5.578 | 0.116 / 0.659 |

残る差には観測時刻ずれ・モデル誤差などが含まれ得るため、ゼロと断言しない。
初回校正点で一致するだけの検証ではなく、独立した異なる20姿勢を使用した。

### 実装と残る制約

OpenWAM configに `calibration_mode: tool` と `joint_signs: [1,1,1,-1,1,-1]` を設定。
IKの全反復、変化量制限後の再最適化、残差判定、CSVのFKは同じ補正済みEEFフレームを使用する。
入力・seed・送信角・変化量上限はROS関節単位のまま、URDF関節範囲も符号に応じて対応付ける。
旧configの既定値はbase補正・符号全+1で互換性を保持する。
校正ログに補正モード・符号・変換行列を追加した。

最新8ステップの理想追従再生（前の新指令を次の実測seedと仮定）:
送信角度のEEF位置残差最大は左2.483 mm、右1.770 mm。全候補が既存許容範囲内。
ただし0番関節の最終角変化は左+30.211°、右-14.125°で、大きな基部回転がなくなる保証ではない。

補正済み運動学で、現初期姿勢から末端姿勢を固定して小移動を解くと:

- +X 20 mm: 0番関節変化は左約-0.2°、右約-0.6°。
- +Y 5 mm: 0番関節変化は左約+19.9°、右約+8.0°。
- +Z 20 mm: 0番関節変化は左右ほぼ0°。

横方向に感度が高い初期姿勢であり、正しい運動学でも微小な横位置・姿勢変化を基部と手首の大きな回転で実現する。
0番関節だけを強く制限しても、元のEEF目標への残差を増やす可能性がある。
基部回転を小さくしたい場合、次は初期姿勢を前へ伸ばす等の姿勢条件の見直しが必要。
ユーザー指定の初期関節値を今回自動では変更していない。
