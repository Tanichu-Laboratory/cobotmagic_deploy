# 右グリッパーが閉じない原因（2026-09-24）

対象: logs/action_commands/action_commands_20260924_033828.csv（225指令）。直前033603も照合。

## 確認結果

- 最新実行は32step消費、5 Hz。右グリッパーはstep0〜22で閉指令0、step23〜26で中間開度、step27以降224まで全開0.06558を送信。
- request2〜8で実行された193指令はすべて全開。IK後のik_joint_right[6]でも全開を確認。
- 実測は概ね0.0649で、全開指令0.06558との差は約0.00068。閉指令を出したのに閉じなかったという証拠はなく、閉じる指令自体がない。
- 初期の閉状態では実測−0.0005。直前033603実行でも243指令すべて閉0で、右実測は−0.0005だった。ただし物体接触時の把持力や機械的な閉じ能力をこの値だけで保証しない。

## 全開へ変換される経路

サーバーの出力変換: physical = clip(model_normalized / 0.75, 0, 1) × 0.06558。
ブリッジ: physical ≤0.025を閉0、physical ≥0.040を全開0.06558、中間はそのまま。
（CSVのright_gripper_rawはモデル生出力ではなくサーバー変換後の実機単位。）

request5末尾(step159)が開いた後で最も閉じる方向に下がる箇所:
model_normalized ≈0.494824 → server 0.043267943 → bridge 0.06558 → 実測約0.0649。
サーバー変換はこの値では飽和していないため、正規化値を逆算できる。
その後のrequest6では再び開側へ戻る。

開き強調後の閾値をモデル正規化値に換算すると、約0.45746以上が全開、約0.28591以下が全閉。
モデルの約0.495という中間開度まで全開化される設定になっている。

requestごとのサーバー開度最小値:
2:0.06558、3:0.06558、4:0.050877、5:0.043268、6:0.060227、7:0.053832、8:0.058122（8は全チャンク値、実行は先頭1指令のみ）。
完了したrequest2〜7では32stepを消費している。保存された全チャンクにも全閉閾値以下の指令はないため、末尾切り捨てによる閉動作喪失ではない。

## 解釈

直接原因は、publish段階で全開指令を送り続けていること。以前導入した開き強調と全開スナップが、モデルの部分的な閉じ方向の変化を打ち消している。
ただしモデル自体も開いた後に全閉に相当する値までは下げていない。
開き倍率だけを元に戻しても最小指令は0.032451になり、現在の全閉閾値0.025には届かない。設定を戻すだけで把持成功するとは断定できない。

次の修正では中間値まで全開へ固定する現設定を見直す必要がある。全閉閾値を根拠なく上げると接近中の早閉じにもなり得るため、対象物到達時のモデル出力と対応づけて決める。
今回は解析のみ。実機publish・運用設定変更なし。
