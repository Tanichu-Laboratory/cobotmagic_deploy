# 関節インデックス3・5の再確認（2026-09-17、100616まで）

結論: 現在の符号対応 `[1,1,1,-1,1,-1]` は最新データでも支持される。
関節の入れ替えを行ったわけではない。一方、別のURDF内部パラメータに小さな系統誤差の原因候補を確認した。
今回の作業はオフライン診断のみ。URDF、運用設定、制御コード、稼働プロセスは変更していない。

## 番号と処理の区別

| ROS配列（0始まり） | URDF名（1始まり） | URDFのaxis | FKへ渡す角度 |
|---:|---|---|---|
| 3 | joint4 | [0,0,-1] | -q_ros[3] |
| 5 | joint6 | [0,0,-1] | -q_ros[5] |

関節の並びはjoint1〜joint6のまま。q[3]とq[5]の交換は行っていない。
FKの内部でROS角をURDF角へ変換する。IKの変数、変化量制限、ROSへの送信はROS角のまま。
`publish_joint_pair` は左右とも得られた関節配列を順番どおり送信する。
「1始まりのjoint3とjoint5を反転する」という意味でもない。

## 独立した新ログでの比較

対象: 100221、100335、100435、100616の4実行、合計116観測。
候補ごとに各実行の実際の初期校正関節/EEFで末端変換を求め、初回観測を除く112観測で検証した。
初回校正点に合うだけの比較ではなく、動いた後の実測関節から予測したEEFを実測EEFと比較する。
左腕の検証データには、例えば最新実行だけでもJ2約94.5°、J3約74°、J4約31°、J6約38°の角度範囲がある。

左腕、全112観測の中央値:

| 関節対応 | 位置誤差(mm) | 姿勢誤差(°) |
|---|---:|---:|
| 現在: インデックス3・5を符号反転 | 1.670 | 1.033 |
| どちらも反転しない | 11.201 | 25.758 |
| 3だけ反転 | 1.752 | 23.722 |
| 5だけ反転 | 12.096 | 9.888 |
| 3と5を交換し、両方符号反転 | 8.726 | 6.231 |
| 3と5を交換し、反転しない | 13.732 | 20.879 |
| 誤って1始まりjoint3・joint5を反転 | 351.169 | 53.666 |

右腕の現在対応は位置中央値4.856 mm・姿勢中央値2.996°、反転なしでは26.228 mm・46.884°。
6軸の符号64通り×交換有無2通り、計128候補も比較した。
位置中央値(mm)＋姿勢中央値(°)という探索用スコアでは、左右とも現在対応が最良。
この混合単位のスコアは物理的な誤差指標そのものではないため、上表の位置・姿勢を別々に評価する。
特に5番の符号誤りは位置誤差だけでは見落としやすく、姿勢誤差の比較が必要。

現在対応の左位置誤差は95パーセンタイル3.917 mm、最大8.104 mm。
最新100616実行だけでは中央値1.808 mm、最大2.851 mm。
符号対応が妥当でも、運動学が完全に一致したわけではない。

## 左方向の残差について新たに見つかった候補

URDFの **joint5（ROSインデックス4）** には、固定originとして
`rpy="1.5708 -0.087266 0"` が設定されている。pitch約−5°は上記3・5番の符号とは別のパラメータ。
このpitchのみをメモリ上で0°へ置き換え、各候補の初期末端校正をやり直す比較を実施した。
URDFファイルそのものは変更していない。

全112観測の中央値:

| URDF joint5の固定pitch | 左 位置(mm) / 姿勢(°) | 右 位置(mm) / 姿勢(°) |
|---|---:|---:|
| 現在 −5° | 1.670 / 1.033 | 4.856 / 2.996 |
| 比較用 0° | 0.437 / 0.128 | 0.893 / 0.025 |
| 比較用 +5° | 1.696 / 1.037 | 4.873 / 3.004 |

最新100616実行の左では:

- 実測EEF−FKのY方向中央値: 現在 +1.470 mm → pitch=0°では −0.114 mm。
- 位置誤差中央値: 1.808 mm → 0.393 mm。

この内部軸の傾きが、数mmの系統誤差の一部を説明する有力候補。
ただしこれはロボットが報告するEEFとの整合性の検証であり、カメラから見た指先と物体の絶対位置の校正ではない。
ベースYの符号と画像上の左右も同一とは限らない。
したがって、ユーザーが観測した把持ずれの全量がこの−5°設定による、とまでは断言できない。
URDFの対象機体仕様との照合、および修正後の実機検証は未実施。

最新実行は既にopen_loop_steps=4、要求間隔中央値約1.200秒。
8ステップの直前3実行は約2.000秒で、以前の32ステップ/約6.8秒だけを今回のずれの説明には使えない。

詳細数値・観測別残差:
`logs/openwam_ik_diagnosis/joint_mapping_recheck_100616.json`。


## 修正の適用

ユーザー指示により、OpenWAM用の補正済みURDFを作成して設定へ適用した。

- 新URDF: `cobotmagic_deployment/assets/piper_description_cobotmagic_joint5_pitch0.urdf`
- 元URDF: `/workspace/project/piper_description_cobotmagic_local_20260529.urdf`（保持）
- 唯一のURDF変更: joint5のorigin rpy `1.5708 -0.087266 0` → `1.5708 0 0`。
- OpenWAM configの `ros.eef_ik.urdf_path` を新ファイルへ変更。
- 関節順、符号 `[1,1,1,-1,1,-1]`、関節範囲、変化量上限は従来どおり。

ROS Python 3.8で実際に新URDFを読み込んで再検証した。
校正点以外の112観測に対するFK位置誤差中央値は左0.437 mm・右0.893 mm。
最新実行の左Y方向残差中央値は−0.114 mm、位置誤差中央値は0.393 mm。
最新136指令を左右それぞれ実測seedから再求解し、全指令が受入判定・関節範囲・変化量上限を満たした。
送信角候補のIK位置誤差最大は左1.544 mm・右3.880 mm。

既存IK・OpenWAM変換/通信テスト47件成功。
履歴再生は旧ログの残差再現に元の関節チェーンを使い、新しい解の計算には設定中の補正済みURDFを使う。
結果: `logs/openwam_ik_diagnosis/joint5_pitch0_applied_100616.json`。

反映にはブリッジの再起動が必要。起動時に新URDFを読み、実測姿勢から末端補正を再校正する。
